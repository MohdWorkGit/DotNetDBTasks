Install and run

IIS hosting and Windows sign-in

One IIS site serves everything: the API answers /api/* and every other address returns the Angular app from the API's own wwwroot. No reverse proxy, no CORS, and domain users are signed in without a form.

التثبيت والتشغيل

الاستضافة على IIS والدخول بحساب Windows

موقع IIS واحد يخدم كل شيء: الـAPI يجيب على /api/*، وأي عنوان آخر يعيد تطبيق Angular من مجلد wwwroot الخاص بالـAPI. بلا وسيط عكسي، وبلا CORS، ويدخل مستخدمو النطاق دون نموذج.

One command

Run elevated, on the server. It builds the client, publishes the API, puts the app into wwwroot, and creates or updates the app pool and site with every setting on this page. Running it again is an upgrade: bindings, appsettings.json, logs\ and cache\ are kept.

أمر واحد

شغّله بصلاحيات المسؤول على الخادم. يبني الواجهة، وينشر الـAPI، ويضع التطبيق في wwwroot، وينشئ مجمّع التطبيقات والموقع أو يحدّثهما بكل إعدادات هذه الصفحة. وتشغيله مرة أخرى ترقية: تبقى الارتباطات وappsettings.json وlogs\ وcache\.

./scripts/deploy-iis.ps1 -Hostname jadwal.corp.local -EnableSso

Why the default app pool is not enough

Three background workers run inside the IIS worker process: the scheduler, the long-query worker and the result-cache upkeep. Their state lives in that process's memory. Three things follow, and none is optional:

لماذا لا يكفي مجمّع التطبيقات الافتراضي

ثلاث عمليات خلفية تعمل داخل عملية IIS نفسها: المجدول، ومنفّذ الاستعلامات الطويلة، وصيانة النتائج المحفوظة. وحالتها في ذاكرة تلك العملية. ويترتب على ذلك ثلاثة أمور، لا يُستغنى عن أي منها:

Exactly one processعملية واحدة بالضبط

A second one runs a second scheduler: every export twice. It also splits the job store, so a browser can ask the wrong process for its result.

العملية الثانية تشغّل مجدولًا ثانيًا: كل تصدير مرتين. وتقسم مخزن المهام، فقد يسأل المتصفح العملية الخطأ عن نتيجته.

No overlapping restartsلا تداخل عند إعادة التشغيل

A starting process clears the result files left behind; with overlap it deletes them while the old one is still sending them.

العملية التي تبدأ تحذف ملفات النتائج المتبقية؛ ومع التداخل تحذفها بينما القديمة ما زالت ترسلها.

Never idleلا خمول أبدًا

An idle pool means the 02:00 export simply does not happen, and nothing reports it.

المجمّع الخامل يعني أن تصدير الساعة 02:00 لا يحدث، ولا يُبلغ عنه شيء.

Building and creating the site by hand

البناء وإنشاء الموقع يدويًا

# Build: client, API, then put the client into the API's wwwroot
cd client; npm run build:prod; cd ..
dotnet publish src/Jadwal.API/Jadwal.API.csproj -c Release -r win-x64 --self-contained -o ./api-publish
New-Item -ItemType Directory -Force .\api-publish\wwwroot | Out-Null
Copy-Item .\client\dist\jadwal-client\browser\* .\api-publish\wwwroot\ -Recurse -Force

# Copy api-publish\ to C:\inetpub\Jadwal, then:
Import-Module WebAdministration
New-WebAppPool -Name "Jadwal"
Set-ItemProperty IIS:\AppPools\Jadwal -Name managedRuntimeVersion -Value ""   # No Managed Code
New-Website -Name "Jadwal" -Port 80 -HostHeader "jadwal.corp.local" `
            -PhysicalPath "C:\inetpub\Jadwal" -ApplicationPool "Jadwal"
icacls "C:\inetpub\Jadwal" /grant "IIS AppPool\Jadwal:(OI)(CI)M" /T              # logs\ and cache\

Edit api-publish\appsettings.json as for any release (step 3); Cors:AllowedOrigins is unused here, since everything is one origin.

Keeping the background workers alive

Apply all of these; the script does. Each answers one of the three needs above.

إبقاء عمليات الخلفية حيّة

طبّق هذه كلها؛ والسكربت يطبّقها. كل منها يلبي واحدًا من الأمور الثلاثة أعلاه.

Import-Module WebAdministration
$p = 'IIS:\AppPools\Jadwal'
# Never idle; start with Windows
Set-ItemProperty $p -Name processModel.idleTimeout -Value "00:00:00"
Set-ItemProperty $p -Name startMode -Value AlwaysRunning
# Exactly one worker process
Set-ItemProperty $p -Name processModel.maxProcesses -Value 1
# No overlapping recycle
Set-ItemProperty $p -Name recycling.disallowOverlappingRotation -Value $true
# No automatic recycles: each drops running jobs and kept results
Set-ItemProperty $p -Name recycling.periodicRestart.time -Value "00:00:00"
Set-ItemProperty $p -Name recycling.periodicRestart.requests -Value 0
Set-ItemProperty $p -Name recycling.periodicRestart.memory -Value 0
Set-ItemProperty $p -Name recycling.periodicRestart.privateMemory -Value 0
Clear-ItemProperty $p -Name recycling.periodicRestart.schedule
# Outer step of the shutdown ladder
Set-ItemProperty $p -Name processModel.shutdownTimeLimit -Value "00:02:00"
# Warm up right after any restart
Set-ItemProperty "IIS:\Sites\Jadwal" -Name applicationDefaults.preloadEnabled -Value $true

The shutdown ladder

A restart is sometimes unavoidable; a deploy is one. Given time, a running export takes the cancel path, records its final status and saves the checkpoints of the items that finished. Killed, it does neither and exports them again next time. Three time limits decide this, and the inner one must be the smallest:

سلّم الإيقاف

إعادة التشغيل لا مفر منها أحيانًا، والنشر مثال عليها. فإن أُعطي التصدير الجاري وقتًا كافيًا، سلك طريق الإلغاء، وسجّل حالته النهائية، وحفظ نقاط توقف العناصر التي اكتملت. وإن قُتل، لم يفعل شيئًا من ذلك وأعاد تصديرها في المرة التالية. ثلاثة حدود زمنية تقرر ذلك، والداخلي يجب أن يكون الأصغر:

  • Give the pool's account write access to every task's output and archive folder. ApplicationPoolIdentity cannot write to network shares; use a domain account for those.
  • A run cut off anyway is closed by the scheduler at the next start: it is marked failed instead of showing "Running" forever.
  • امنح حساب المجمّع صلاحية الكتابة في مجلد الإخراج والأرشيف لكل مهمة. والحساب ApplicationPoolIdentity لا يكتب في مجلدات الشبكة؛ فاستخدم حساب نطاق لها.
  • التشغيل الذي انقطع رغم ذلك يغلقه المجدول عند البدء التالي: يُعلَّم فاشلًا بدل أن يظهر «قيد التشغيل» إلى الأبد.

Windows sign-in

Off by default. Set "Auth": { "EnableSso": true } in appsettings.json. While off, the endpoint answers 404 and people sign in with their directory user name and password, checked against LDAP; no IIS Windows-authentication setup is needed for that.

When on, the sign-in page tries GET /api/auth/sso by itself as it loads. A domain-joined browser sends its Kerberos or NTLM ticket, the account is created or refreshed from the directory, and Jadwal issues its own token. People arrive signed in and never see the form. If the attempt fails, the form simply appears.

  • Signing out does not bounce you straight back in: the automatic attempt is skipped for the rest of the browser session.
  • ng serve cannot test this; it only works in this IIS setup.
  1. Unlock the authentication sections once per server, or IIS answers 500.19: appcmd unlock config /section:windowsAuthentication and the same for anonymousAuthentication (in %windir%\system32\inetsrv). The shipped web.config then turns both on.
  2. Reach the site by host name, not IP, and put that host in the browser's Local Intranet zone; otherwise the browser asks for a password.
  3. A custom domain account for the pool needs an SPN: setspn -S HTTP/jadwal.corp.local DOMAIN\svc-account.
  4. Keep Ldap:* valid: the ticket gives the user name, the profile still comes from the directory. Prefer HTTPS.

الدخول بحساب Windows

متوقف افتراضيًا. اضبط "Auth": { "EnableSso": true } في appsettings.json. وما دام متوقفًا، تجيب نقطة الوصول بـ404، ويدخل الناس باسم المستخدم وكلمة المرور في الدليل، ويُتحقق منهما عبر LDAP؛ ولا يحتاج ذلك أي إعداد لمصادقة Windows في IIS.

وعند تفعيله، تحاول صفحة الدخول GET /api/auth/sso بنفسها عند تحميلها. فيرسل المتصفح المنضم إلى النطاق تذكرة Kerberos أو NTLM، ويُنشأ الحساب أو يُحدَّث من الدليل، ويصدر «جدول» رمزه الخاص. فيصل الناس وقد سجّلوا الدخول دون أن يروا النموذج. وإن فشلت المحاولة يظهر النموذج ببساطة.

  • تسجيل الخروج لا يعيدك إلى الداخل فورًا: تُتجاوز المحاولة التلقائية حتى إغلاق المتصفح.
  • لا يمكن اختبار ذلك بـng serve؛ فهو لا يعمل إلا في هذا الإعداد على IIS.
  1. افتح أقسام المصادقة مرة واحدة لكل خادم، وإلا أجاب IIS بـ500.19: appcmd unlock config /section:windowsAuthentication والأمر نفسه لـanonymousAuthentication (في %windir%\system32\inetsrv). ثم يفعّل ملف web.config المرفق الاثنين.
  2. ادخل إلى الموقع باسم المضيف لا بعنوان IP، وضع ذلك المضيف في منطقة الإنترانت المحلية في المتصفح؛ وإلا طلب المتصفح كلمة مرور.
  3. حساب نطاق مخصص للمجمّع يحتاج SPN: setspn -S HTTP/jadwal.corp.local DOMAIN\svc-account.
  4. أبقِ Ldap:* صحيحًا: التذكرة تعطي اسم المستخدم، والملف الشخصي ما زال يأتي من الدليل. ويُفضَّل HTTPS.

Checking it worked

The basics: the site opens and a deep link like /admin/queries survives a refresh; /swagger shows the API; start-up failures appear in Event Viewer → Windows Logs → Application and the app's own log in logs\. A dashboard's tiles fill in and then refresh by themselves.

Three checks actually prove the setup, and are worth doing before calling it finished:

  1. The workers survive idleness. Leave the site untouched for 30 minutes or more, then confirm a scheduled task still ran.
  2. A long query completes. Run one that takes over two minutes; it should finish and page normally.
  3. A recycle behaves. With a task every 5 minutes, run Restart-WebAppPool Jadwal mid-run. The interrupted run should show Canceled or Failed, the next one should fire within about 30 seconds, with no duplicate and no cut-off file.

التحقق من النجاح

الأساسيات: يفتح الموقع، ويبقى رابط داخلي مثل /admin/queries يعمل بعد التحديث؛ وتعرض /swagger الـAPI؛ وتظهر أخطاء البدء في Event Viewer ← Windows Logs ← Application وسجل التطبيق في logs\. وتمتلئ بطاقات لوحة المعلومات ثم تتحدث وحدها.

ثلاثة فحوص تثبت الإعداد فعلًا، وتستحق التنفيذ قبل اعتباره منتهيًا:

  1. عمليات الخلفية تصمد أمام الخمول. اترك الموقع دون استخدام 30 دقيقة أو أكثر، ثم تأكد أن مهمة مجدولة قد عملت.
  2. استعلام طويل يكتمل. شغّل استعلامًا يستغرق أكثر من دقيقتين؛ يجب أن ينتهي ويُتصفح طبيعيًا.
  3. إعادة التدوير تمر بسلام. مع مهمة كل 5 دقائق، نفّذ Restart-WebAppPool Jadwal أثناء التشغيل. يجب أن يظهر التشغيل المقطوع ملغى أو فاشلًا، وأن يبدأ التالي خلال نحو 30 ثانية، دون ملف مكرر أو مبتور.
